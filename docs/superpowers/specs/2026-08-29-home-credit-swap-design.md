# SmartLend — Swap Live Pipeline from Synthetic Data to Home Credit

**Design specification**
**Date:** 2026-08-29
**Status:** Approved for implementation planning
**Relationship to prior spec:** Complements `2026-08-18-conformal-credit-deferral-design.md`.
That spec is the 32-week research thesis (conformal deferral guarantees under
selection bias, four datasets, C1-C8 work packages). This spec is narrower and
more immediate: get the *live backend/frontend app* off self-generated data and
onto Home Credit now, since every current dashboard number, model metric, and
the Week-1 deferral-rule chart currently trace back to a hand-tuned random
generator.

## 1. Context

`backend/training.py` trains all 5 models (CatBoost, LightGBM, XGBoost,
RandomForest, LogisticRegression) plus CBES plus the deferral logic on
`synthetic_indian_loan_dataset.csv` — 25,000 fabricated rows generated by
`backend/generate_indian_loan_dataset.py` from hand-picked logistic-model
intercepts (`RISK_INTERCEPT = -2.85`). No result computed on it is defensible
in a paper.

Two more problems compound this:

- **Two divergent training pipelines exist today.** `training.py` predicts
  `loan_approved`; `backend/app/services/ml_service.py` and
  `backend/retrain_pipeline_v2.py` predict `default_risk`. Different targets,
  different feature sets, no reconciliation.
- **CBES's rule vocabulary is India-specific** (`cibil_score`,
  `residential_assets_value`, `commercial_assets_value`, ...) and has no
  equivalent in Home Credit, which is an EU consumer-finance dataset with no
  bureau score, no asset-value fields, and no approve/reject label at all
  (`application_train.csv` contains only already-accepted loans).

`research/data/` (canonical.py, adapters.py, specs/home_credit.py, cli.py) is
already built and validated against the real files (`data/raw/home_credit/`:
`application_train.csv`, 307,511 rows x 122 cols; `bureau.csv`, 17 cols) — see
`reports/home_credit_coverage.csv` and `reports/home_credit_missingness.csv`
from the validation run on 2026-08-29. This spec is mostly about wiring that
existing layer into the live app and redesigning CBES around it, not building
new data infrastructure from scratch.

## 2. Decisions (already approved in discussion)

1. **CBES's score rule** is redesigned from scratch around Home Credit fields
   (`credit_score` = `EXT_SOURCE_2` proxy) using data-driven percentile bands
   computed from the training distribution, documented as dataset-derived
   thresholds — not presented as a real bank/bureau convention.
2. **Single prediction target: default risk only** (`TARGET` from
   `application_train.csv`). `loan_approved` is retired; Home Credit cannot
   support an approval-decision label, and the Week-1 research question is
   about risk prediction, not approval prediction.
3. **Data layer**: use `research/data/adapters.build_bundle()` as-is. Add one
   new module, `research/data/bureau_aggregates.py`, that groups `bureau.csv`
   by `SK_ID_CURR` to populate `delinquencies` (count of
   `CREDIT_DAY_OVERDUE > 0`) and `active_loans` (count of
   `CREDIT_ACTIVE == 'Active'`). `credit_utilization` stays `ABSENT`
   (`credit_card_balance.csv` was not fetched) — CBES simply has no
   utilization rule.
4. **CBES rule set**: 7 rules built only from real fields — `credit_score`
   (percentile-based), `delinquencies`, `active_loans`, `dti`,
   `employment_tenure_years`, an income/loan-amount affordability check, and
   an optional low-weight `region` (urbanicity proxy) rule. No substitute is
   invented for `credit_utilization` or asset value — those rules are dropped,
   not faked. Thresholds are computed by a calibration script (same pattern as
   the existing `calibrate_tau_d`), not hand-picked.
5. **Synthetic files are deleted now** (`synthetic_indian_loan_dataset.csv`,
   `backend/generate_indian_loan_dataset.py`), per explicit instruction.
   **Caveat, logged here for traceability:** the 2026-08-18 spec (section
   "The synthetic generator is repurposed, not discarded", work package C4)
   requires a synthetic dataset with *known ground-truth propensity* for later
   validation of the conformal-correction method — that generator does not
   exist elsewhere. Deleting it now means **C4 will need a new synthetic
   generator built from scratch** when that phase starts; this is a deliberate
   trade-off, not an oversight, and should be called out again when C4 begins.

## 2a. Amendment (2026-08-30): model training is out of scope for this pass

Descoped by explicit instruction: **no model is trained in this pass.** The
5-model ensemble, SHAP-based feature selection, and the production-model
retrain (all of former section 3.1) are deferred to a later task, once
HuggingFace model(s) are chosen. SHAP cannot run without a trained model, so
it is deferred along with training, not attempted some other way.

This pass's job is narrowed to three things, all model-free:
1. **Data cleaning** — sentinel handling, dtype fixes, missingness treatment
   (`research/data/profile.py` already does most of this; extend as needed).
2. **Derived/aggregated columns** — the canonical derivations already in
   `research/data/specs/home_credit.py` (`age_years`, `dti`,
   `employment_tenure_years`) plus the new `bureau_aggregates.py` (section
   3.2 below).
3. **CBES logic redesign** — replace the synthetic-vocabulary rules with the
   7-rule design (section 3.3), including its percentile-threshold
   calibration. CBES rules are hand-designed heuristics over derived columns,
   not a trained model, so this does not depend on the deferred training work.

`run_evaluation.py`, `compute_baselines.py`, `training_comparison.py`,
`run_calibration_report.py`, and the "consolidated training pipeline" —
untouched in this pass. They still point at the synthetic dataset today and
will break once that file is deleted (section 3.5); fixing them requires the
deferred training work, so for now they are either left broken with a clear
`NotImplementedError`/README note, or excluded from the current import path
so the rest of the app doesn't crash on import. Decide exact handling during
implementation planning.

## 3. Architecture (this pass — no training)

### 3.1 Data cleaning + derived/aggregated columns
Extend `research/data/` rather than duplicate it:
- Sentinel/missingness handling: already covered by `research/data/profile.py`
  and the `DAYS_EMPLOYED` sentinel logic in `specs/home_credit.py`; extend to
  any other sentinel-like columns the missingness profile flags
  (`reports/home_credit_missingness.csv` already lists candidates —
  `sentinel_coded`/`mar_candidate` rows).
- New module `research/data/bureau_aggregates.py`: groups `bureau.csv` by
  `SK_ID_CURR`, returns `delinquencies` (count `CREDIT_DAY_OVERDUE > 0`) and
  `active_loans` (count `CREDIT_ACTIVE == 'Active'`), joined onto the
  canonical `core` frame from `build_bundle()`. This is the only new
  data-engineering code this pass needs.
- No feature reduction / SHAP here — the full derived+native column set is
  left as-is for whichever model gets trained later.

### 3.2 CBES engine redesign
`backend/app/services/cbes_engine.py`'s input dict changes from the 15-key
synthetic vocabulary to the 7 fields from decision 4: `credit_score`
(percentile-based, from `EXT_SOURCE_2`), `delinquencies`, `active_loans`
(from 3.1), `dti`, `employment_tenure_years`, an income/loan-amount
affordability check, and optional low-weight `region`. A new calibration
script (mirroring the existing `calibrate_tau_d` pattern) computes the
percentile-band thresholds from the real Home Credit distribution — nothing
hand-picked, nothing copied from the synthetic version. This is pure
rule-logic + derived-column work; it does not require a trained model and is
not part of the deferred training work.

### 3.3 API / frontend schema (interim)
Since the SHAP-selected "top 15-20" feature list no longer exists this pass
(deferred with training), the interim application-facing schema is the
**canonical core** (the 9 populated fields from `research/data/canonical.py`:
`age_years`, `annual_income`, `loan_amount`, `installment`, `credit_score`,
`dti`, `employment_tenure_years`, `gender`, `region`, plus `delinquencies` /
`active_loans` from 3.1) — i.e. exactly what CBES itself consumes. This is a
placeholder schema, expected to be superseded once the deferred SHAP pass
picks a production feature set. `backend/app/schemas.py`
(`LoanApplicationInput`), `public_api_service.py`'s alias/normalize map, the
frontend form, `training_data_service.py`, and `explainability_service.py`
are rewritten against this interim set, dropping the India-specific fields
that no longer exist (CIBIL score, residential/commercial asset value).

**Known pre-existing bug, worth checking, not necessarily fixing this pass:**
the exploration found `public_api_service.py` passes camelCase keys into
`predict_application`, while `ml_service.feature_names` are snake_case
training-CSV columns — these likely never match, so live predictions may
already be silently falling back to CBES defaults for most features. Since
`ml_service`/model inference is part of the deferred training work, full
resolution waits — but the rewritten schema in this pass should not
*introduce* the same mismatch again.

### 3.4 Retirement
Delete `synthetic_indian_loan_dataset.csv` and `backend/
generate_indian_loan_dataset.py` now (per 2a's caveat about the 2026-08-18
spec's C4 need — logged, accepted). Leave `backend/retrain_pipeline_v2.py`,
`run_evaluation.py`, `compute_baselines.py`, `training_comparison.py`,
`run_calibration_report.py`, and `ml_service.py`'s `train_pipeline` in place
but non-functional against the new schema — do not fix them this pass (that's
training work); instead give each a short top-of-file note pointing at this
spec, so nobody mistakes "unmaintained" for "abandoned."

### 3.5 Testing
- Unit tests for `bureau_aggregates.py` (small fixture: a few `SK_ID_CURR`
  values with hand-computed expected counts).
- Unit test for the CBES percentile-threshold calibration (thresholds land
  where expected on a known percentile fixture).
- One integration check: build the interim canonical-core record for a
  sample of real rows, run it through `cbes_engine` -> `hybrid_decision`
  (with a stubbed/fixed `p_ml`, since no model is trained this pass) and
  confirm it produces a decision without key errors.
- Manual run: start the frontend against the updated API with the interim
  schema, submit one application, confirm CBES's explanation renders (ML
  probability can be stubbed/mocked for this pass).
